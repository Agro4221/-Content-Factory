# Участие в разработке

Content Factory — приложение для сбора публикаций из Telegram, подготовки текста с помощью локальной или облачной AI-модели и публикации в целевые каналы. Публичная сборка ориентирована на Windows 10/11.

## Подготовка изменений

Перед отправкой pull request:

1. Убедитесь, что изменение решает одну понятную задачу.
2. Добавьте или обновите тесты для изменённого поведения.
3. Обновите документацию, если меняются настройки, формат данных или интерфейс.
4. Убедитесь, что локальные данные и секреты не попали в diff.
5. Запустите проверки:

   ```powershell
   python -m pytest -q tests
   python -m ruff check .
   python -m mypy
   python tools/check_frontend.py
   python tests/check_for_secrets.py
   ```

В pull request кратко опишите назначение изменения, пользовательские последствия и выполненные проверки.

## Соглашения по коду

- Используйте Python 3.11 или новее.
- Имена модулей, функций и переменных — на английском языке. Тексты интерфейса и пользовательские сообщения — на русском.
- Комментарии должны объяснять назначение кода, ограничения и неочевидные решения. Не используйте комментарии для описания истории разработки или процесса внесения изменений.
- Миграции схемы добавляйте в `database.py` с новым номером версии. Не изменяйте номера уже выпущенных миграций.
- Не добавляйте зависимости без необходимости. Учитывайте влияние пакетов на сборку Windows EXE.
- Не включайте в коммиты рабочие файлы: `.env`, `bot_storage.db`, файлы сессии Telethon (`*.session`), каталоги виртуального окружения и артефакты сборки.

## Структура проекта

```text
main.py            обработка источников и публикация постов
Site.py            веб-панель и API
admin.html         интерфейс управления
database.py        SQLite, схема и миграции
secrets_store.py   шифрование секретов через Windows DPAPI
routing.py         маршрутизация публикаций по тегам
config.py          настройки и пути
tests/             автоматические проверки
tools/             проверка окружения и сборки
```

## Обсуждение

Для сообщений об ошибках и предложений используйте GitHub Issues. Крупные изменения поведения или API лучше предварительно описать в отдельном Issue.
